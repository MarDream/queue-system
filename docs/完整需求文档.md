## 2. 项目概述

### 2.1 项目背景

线下服务大厅（如银行、政务中心、医院）在高峰时段存在等待时间长、排队秩序混乱、窗口利用率不均等问题，需要通过统一的排队叫号系统提升服务效率和现场秩序。

### 2.2 项目目标

- 支持现场取号
- 支持排队状态查询
- 支持柜台叫号、重呼、跳过、开始服务、完成服务
- 支持管理后台对业务类型、柜台、区域、用户等基础数据进行管理
- 支持显示大屏展示当前叫号与等待情况
- 支持管理员批量导入用户账号

### 2.3 技术架构

| 层级 | 技术选型 |
| --- | --- |
| 前端 | Vue 3 + Vite + Element Plus |
| 后端 | Spring Boot 3 + MyBatis-Plus |
| 数据库 | MySQL 8.0 |
| 缓存 | Redis |

## 5. 核心业务流程

### 5.1 现场取号流程

```text
用户选择业务类型 → 生成票号（业务前缀 + 当日序号）
→ 进入等待队列 → 返回票号、等待人数、预计等待时间
```

### 5.2 叫号流程

```text
柜台人员点击叫号 → 系统从柜台支持的业务队列中选取最早等待用户
→ 更新票号状态为已叫号 → 显示大屏展示当前叫号信息
→ 柜台人员开始服务 / 跳过 / 完成服务
```

### 5.3 票号状态流转

```text
WAITING（等待）
  ├── → CALLED（已叫）
  │       ├── → SERVING（服务中）
  │       │       └── → COMPLETED（已完成）
  │       └── → SKIPPED（跳过）
  └── → CANCELLED（取消）
```

### 5.4 多业务柜台叫号规则

- 一个柜台可绑定多个业务类型
- 叫号时从该柜台支持的多个业务队列中选择创建时间最早的等待票
- 通过分布式锁避免并发下重复叫号

## 6. 功能模块需求

### 6.1 用户端

#### 6.1.1 现场取号

- 展示已启用业务类型
- 展示各业务当前等待人数
- 生成唯一票号
- 返回前方等待人数与预计等待时长
- 同一手机号同一业务类型仅允许持有一个有效等待票

#### 6.1.2 排队状态查询

- 支持按票号查询当前状态
- 显示票号状态、办理窗口、等待人数等信息

#### 6.1.3 取消排队

- 允许取消仍处于等待状态的票号

### 6.2 显示大屏

- 展示当前叫号信息
- 展示窗口与票号对应关系
- 展示等待队列概要数据
- 当前阶段采用轮询获取数据，不使用 WebSocket

### 6.3 柜台端

- 叫下一个号
- 重呼当前号
- 跳过当前号
- 开始服务
- 完成服务
- 切换暂停/空闲状态

### 6.4 管理后台

#### 6.4.1 仪表板

- 今日取号总数
- 已完成数量
- 等待中数量
- 平均等待时长
- 平均服务时长

#### 6.4.2 业务类型管理

- 业务类型增删改查
- 管理名称、前缀、描述、启用状态、排序

#### 6.4.3 柜台管理

- 柜台增删改查
- 管理窗口编号、名称、状态、支持业务类型

#### 6.4.4 区域管理

- 区域增删改查
- 支持区域层级或业务归属管理

#### 6.4.5 用户管理

- 用户增删改查
- 角色管理
- 用户状态管理
- 用户批量导入

## 8. 数据模型需求

### 8.1 核心业务表

- `business_type`：业务类型
- `counter`：柜台
- `counter_business`：柜台与业务类型关系
- `ticket`：排队票号
- `appointment`：预约记录（表存在，当前阶段未启用业务闭环）
- `sys_config`：系统配置（表存在，当前阶段未启用运行时读取）

### 8.2 用户与区域相关表

- 用户表：存储系统登录用户、角色、状态、所属区域等信息
- 区域表：存储区域信息及管理范围

### 8.3 数据约束

- 票号格式：`{prefix}{sequence}`，如 `A008`
- 序号按天重置
- 所有实体启用乐观锁字段 `version`
- 所有实体支持逻辑删除字段 `deleted`

## 9. 非功能性需求

### 9.1 性能

- 取号与叫号接口应保持较快响应
- 支持服务大厅场景下的并发排队与查询

### 9.2 并发控制

- 取号序号通过 Redis 原子递增生成
- 柜台叫号通过分布式锁控制并发
- Redis 不可用时可降级到数据库逻辑

### 9.3 数据安全

- 手机号展示时脱敏
- 管理能力需按角色与区域权限控制

### 9.4 可维护性

- 统一返回结构
- 统一异常处理
- 文档需明确区分当前能力与规划能力

## 10. 当前专题文档

### 10.1 用户批量导入

#### 业务目标

允许管理员通过 Excel 模板批量创建系统用户，降低人工录入成本，提升初始建档效率。

#### 适用角色

- 超级管理员：可导入所有区域、所有允许角色
- 区域管理员：仅可导入其管理范围内用户，且不能导入 `REGION_ADMIN`

#### 功能范围

- 下载 Excel 导入模板
- 上传 Excel 文件并校验内容
- 批量创建用户
- 对未填写初始密码的用户自动生成密码
- 返回导入结果与自动生成密码清单

#### 数据校验规则

- 用户名必填且唯一
- 姓名必填
- 角色必填且必须为允许值
- 区域 ID 必填且必须存在
- 邮箱如填写则必须唯一
- 密码如填写则长度至少 6 位
- 状态如填写则必须为允许值

#### 处理规则

- 任意一行失败则整批回滚
- 导入结果需明确提示错误行号与原因
- 自动生成密码仅在导入成功后展示一次

### 12.1 微信网页授权扫码取号建设方向

后续移动端建议建设独立于后台管理员体系的公共用户身份层，用于承载微信内扫码取号、预约取号、我的排队、我的预约等能力。

建设原则如下：

- 微信内优先走公众号网页授权，推荐先通过 `snsapi_base` 获取 `openid`
- 后端建立公共用户会话，不直接复用后台登录态
- 首次授权后补充绑定手机号及必要资料，后续复用统一身份
- 非微信环境需提供手机号验证码等降级登录方案

详见专题文档：
