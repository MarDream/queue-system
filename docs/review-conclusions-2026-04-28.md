# 排队系统 Review 结论

日期：2026-04-28

## 1. 本轮结论范围

本结论覆盖以下内容：

- 当前前后端代码的功能 review
- 响应性能与高并发路径风险
- 权限与数据安全边界
- 手机号存储方案
- 二维码公网开放边界

## 2. 已确认的业务与安全结论

### 2.1 手机号存储

手机号需要可逆加密存储，且在必要时可以解密查看。

最终方案：

- 数据库不再只存脱敏手机号
- 同时存储以下字段
  - `phone_ciphertext`：密文手机号
  - `phone_hash`：用于精确查重和查询的不可逆摘要
  - `phone_masked`：展示用脱敏值
  - `phone_last4`：后四位，供人工核对或有限检索
  - `phone_key_version`：密钥版本
- 查重、活动票查询、我的票查询统一基于 `phone_hash`
- 默认列表页不返回解密手机号
- 解密查看必须是单独的高权限能力，并记录审计日志

补充说明：

- 不能继续把脱敏手机号当作业务主键，否则不同用户可能发生冲突
- 密文不适合作为查询条件，查询键必须独立设计

### 2.2 二维码公网开放

二维码需要支持公网访问，这一点确认保留。

最终边界：

- 公开开放：纯读取、无副作用的二维码生成接口
  - 例如：`GET /api/v1/qrcode/generate`
- 不公开开放：任何会写库、列记录、列清单、删除记录的管理接口
  - `url`
  - `list`
  - `delete`
  - `batch delete`

补充要求：

- 公开二维码接口应增加缓存策略
- 公开二维码接口应增加限流
- 公开接口不得顺带写入 `QrCodeRecord`

## 3. 本轮 review 的核心问题结论

### 3.1 最高优先级

1. 管理接口权限边界不可靠，很多地方依赖前端传 `userId` 决定权限范围。
2. 二维码控制器当前开放范围过大，管理能力与公网能力混在同一个入口下。
3. 窗口叫号状态机不严谨，窗口处于 `busy` 时仍可能再次 `callNext`。
4. 手机号模型设计错误，脱敏值被当作查重与查询键使用。

### 3.2 性能热点

1. 统计接口先查全量再内存分页，数据量变大后响应会明显下降。
2. 登录链路中挂了历史票据全表扫描，不应放在用户登录路径上。
3. 大屏接口和窗口页接口存在“拉当天全量票据后再内存聚合”的实现。
4. 前端多个页面固定间隔轮询，窗口页还存在重复取数和宽接口取数问题。
5. 前端生产包体偏大，主包已超过合理首屏范围。

### 3.3 逻辑严谨性问题

1. 预约页等待中自动刷新条件与后端状态值大小写不一致，实际会导致等待中不自动轮询。
2. 窗口页等待队列过滤逻辑不够严谨，存在把其他区域票据混入当前窗口视图的风险。
3. Redis 队列状态与数据库状态的修改需要更严格的事务边界和幂等约束。

## 4. 落地改造原则

### 4.1 权限原则

- 所有管理权限必须以后端登录态为准
- 不再依赖前端 query 参数中的 `userId` 作为权限依据
- 公网接口与后台管理接口彻底分离

### 4.2 性能原则

- 尽量把聚合、分页、过滤下推到 SQL
- 热路径接口只返回当前页面真正需要的数据
- 避免“全量拉取再前端过滤”
- 高频轮询接口必须收窄字段、缩小范围，并考虑退避或事件推送

### 4.3 敏感数据原则

- 明文手机号不入库
- 脱敏值仅用于展示
- 查询与去重使用摘要字段
- 解密能力最小授权并留痕

## 5. 建议的整改优先级

### P0

1. 收紧二维码接口边界
2. 移除所有基于 query `userId` 的权限判断
3. 修复窗口叫号状态机与并发保护
4. 重构手机号字段模型

### P1

1. 重写统计查询为数据库分页和数据库聚合
2. 去掉登录时历史票全表扫描
3. 为窗口页提供专用轻量快照接口
4. 修复预约页状态值不一致问题

### P2

1. 压缩前端包体
2. 减少前端 localStorage 高频写入
3. 合并和优化轮询策略
4. 逐步补齐后端服务层和关键状态流转测试

## 6. 当前验证结果

- 后端编译通过：`mvn -q -DskipTests compile`
- 前端构建通过：`npm run build`
- 后端当前没有有效测试用例文件
- 前端当前没有测试目录

## 7. 下一步建议

建议按以下顺序执行：

1. 先做权限与二维码边界整改
2. 再做手机号密文化与查询键改造
3. 再做窗口/大屏/统计三条热路径性能优化
4. 最后做前端包体与轮询治理
